# SDK bot notes (claude-agent-sdk 0.2.168, bundled Claude Code CLI 2.1.301)

- Not `dontAsk` mode, on purpose. `.claude/settings.json` has an `ask` rule for `mcp__heygen__start_video_render`, and `dontAsk` turns every `ask` into a refusal before anything else is consulted. Tried on 2026-10-19: a hook returning `allow` and a `can_use_tool` callback both fail to get past it, and the producer reports "you haven't granted it yet". The bot runs in `default` mode and `claude_tools.authorize` (`can_use_tool`) is the allow list; it is asked for every tool call that isn't already allowed. Don't add `allowed_tools`: it would skip the callback for those tools.
- A hook cannot grant what an `ask` or `deny` rule refuses, but it can always deny. So the rules that must hold unconditionally are PreToolUse hooks (`render_gate`, `file_guard`): they also fire inside subagents and for edits a subagent's `permissionMode: acceptEdits` (set in its agent file) accepts without asking `authorize`. Tested live: a Write outside `workspace/` is denied in `acceptEdits` mode. A render is checked four times (the terminal hook from settings, `render_gate`, `authorize`, and inside the tool), all through `.claude/hooks/approval.py`. Keep them all calling that one rule.
- The lead runs from `lead_definition()`, not straight from `.claude/agents/lead.md`. Its `initialPrompt` ("list the jobs and ask which to continue") is attached by Claude Code to the first message of every new session, also through the SDK, and the lead obeys it instead of starting the user's job (tried; telling it to ignore the instruction in the appended prompt did not help). The definition is the file minus `initialPrompt`, with the same name so it wins, and read fresh every turn. `omitClaudeMd` has no effect on a main-session agent, so nothing is lost there. If lead.md gains a frontmatter key, map it in `lead_definition`; unmapped keys are dropped silently.
- `setting_sources=["project"]` loads everything in `.claude/settings.json`, hooks included. `smoke_gate.py` and `session_next_task.py` exit at once when `CLAUDE_AGENT_SDK_VERSION` is set (the SDK sets it for its child process); without that, every turn would run the smoke test at the end and the lead would be told the learning path's next task. A new hook in settings.json that is only meant for development needs the same check.
- `strict_mcp_config=True` ignores `.mcp.json`, whose stdio `heygen` server would clash with the in-process one. The server is named `heygen` so tool names match the `mcp__heygen__*` lists in the agent files. The scout's inline Tavily server (from its agent file) still starts and uses `TAVILY_API_KEY`, which is the one key `CHILD_ENV` leaves in place.
- Subagents run in the background in this CLI version: the lead's turn ends with a `ResultMessage` right after it launches one, and the same `query()` stream goes on with a new init frame and result when the subagent finishes. So one user message yields several `ResultMessage`s; `handle_turn` checks each, and `max_budget_usd` and `max_turns` count across the whole stream.
- Text is posted live, as it arrives, under the persona found from `parent_tool_use_id` (needs `forward_subagent_text=True`). A specialist's last message is addressed to the lead, so every task the lead gives ends with a sentence telling it the reply is posted for the user (`DISCORD_PROMPT`). The prompt constant lives in claude_bot.py, not `personas/`, because every file there must be named after a persona key.
- No Bash: Discord text is untrusted and a shell turns one injection into code execution. The producer's `count_words.py` helper is therefore unavailable; `set_video_plan` (and `file_guard` for a plain Write) enforce the 50-word cap instead. Notion is not connected, so the lead is told not to offer publishing.
- Sessions: channel id -> session id in `claude_sessions.json` (gitignored). Claude Code deletes old session files (30 days by default) and resuming a missing one raises on every message, so `resume_id` starts a new session when `get_session_info` can't find it. Bot sessions live in the same `~/.claude/projects/` folder as development sessions. `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` keeps the bot from reading or writing the developer's auto memory.
- `.claude/hooks/loop_cap.py` keeps one state slot, keyed by session id. With two channels working at once the slot flips between them and resets, so the cap gets weaker (never stricter).
- The render watcher (`claude_tools.watch_render`) is plain asyncio and dies with the bot process, like `tools._watch_render`. It posts as the producer through the `notify` closure that `handle_turn` builds, so the channel is never model input. A render started before a restart is only recovered through `check_video_status`.
- Webhooks: `get_webhook` reuses only a webhook named "AI Company Webhook" that has a token. Discord shows the token only to the bot that created the webhook, so one made by another bot (`discord_bot.py`'s, the Discord plugin's) is listed without it and `send()` raises "This webhook does not have a token associated with it". A channel can therefore end up with one webhook per bot, which is fine (Discord allows 15). `discord_bot.py` has the same lookup without the check, so it fails the same way if it ever runs on a bot that didn't create the webhook. The bot also needs Manage Webhooks in the channel (403 Missing Permissions otherwise).
- Runs on a personal Claude login only. Serving other people needs an Anthropic API key (`ANTHROPIC_API_KEY`). Use a different bot token from `discord_bot.py` (`CLAUDE_BOT_TOKEN`) or both bots answer every message, and set `CLAUDE_BOT_CHANNEL_IDS` before inviting anyone else.
- `scripts/claude_bot_test.py` is offline (scripted SDK stream, fake Discord and HeyGen) and covers the guards, tools, persona routing, sessions and lock. The `Stop` hook does not run it, only `scripts/smoke_test.py`.
